Job Board with AI-Powered Candidate Matching

Repo: empty, no commits DB: SQLite Auth: JWT AI: OpenRouter, with fallback Target: same-day, full scope

Context

The repository has no commits and no files — git log on develop returns "does not have any commits yet". Everything below is new work, not a refactor. The system needs two roles (Company Admin, Candidate), full CRUD on jobs and applications, an admin analytics dashboard, and an AI feature that turns a natural-language job preference into a ranked, explained list of open jobs. It is evaluated on a live Teams call today, so it has to start reliably on a clean machine on both Windows and Ubuntu, and every important decision has to survive being questioned live.

Confirmed decisions

DecisionChoice
AI providerOpenRouter free-tier key, behind a provider abstraction with a deterministic fallback
AuthLightweight JWT — email/password, role enforced server-side on every admin endpoint
DatabaseSQLite — driver is in the Python standard library on both operating systems
TimelineSame day — full scope: tests, polished UI, slides, demo script

Assumptions

  1. One admin account maps to one company (set at registration); an admin sees and edits only their own jobs. Candidates browse open jobs from all companies.
  2. Education and project summaries are stored as JSON columns on the candidate profile, not separate tables — they are only ever read as part of the whole profile, never queried independently.
  3. JWT auth is real but minimal: no refresh tokens, no email verification, no password reset. Tokens last 12 hours and live in localStorage.
  4. An application stores a snapshot of the candidate's profile at submit time, so later profile edits don't rewrite what the admin reviewed.
  5. AI matching considers only jobs with status = open.
  6. Application status pipeline: applied → shortlisted | rejected, shortlisted → rejected. rejected is terminal. Any other transition returns an error naming the allowed set.
  7. No salary field — not requested in the brief, so it isn't invented.

Risks and how they're handled

RiskHandling
OpenRouter free tier rate-limits or hangs mid-demoLLM is never on the critical path: 8-second timeout, deterministic fallback for both intent extraction and explanation. The demo is tested with the key removed entirely.
LLM invents a skill or fact in an explanationExplanations are template-built from the score breakdown by default. An optional LLM rewrite is checked against the breakdown's facts and discarded if it adds anything new.
Native dependency fails to install on WindowsPasswords hashed with hashlib.scrypt (standard library) instead of bcrypt/passlib. SQLite driver is standard library. No native wheels anywhere in the dependency list.
Ranking logic is hand-wavy under questioningEvery score is a breakdown with per-component values, returned by the API and shown in the UI. The weights are pinned by unit tests.
Time pressure leaves the UI half-wiredBuilt as vertical slices — API, client, and page together, verified before the next slice starts.
Thin seed data makes matching and charts look emptySeed script writes 5 companies, ~18 jobs across distinct domains, 6 candidates, and ~20 applications spread across all three pipeline states.

Routers do auth, validation, and call one service method. Services own all business rules and database access. matching/score.py is pure — no database, no network, no I/O — which is what makes it unit-testable.

AI matching workflow

query --> extract_intent() --> MatchIntent{roles, skills, experience, locations, domains, type}
            +- LLM (OpenRouter, strict JSON, 8s timeout, Pydantic-validated)
            +- fallback: deterministic keyword extractor (vocab from DB distinct values)
                                  |
profile --> merge_intent() -------+  query wins; profile fills gaps at 0.6 weight
                                  v
open jobs --> score_job(intent, profile, job) -> ScoreBreakdown   [pure, tested]
                                  v
            rank, band, explain(breakdown)  [template; optional LLM rewrite, fact-checked]

Scoring weights (sum to 100)

ComponentWeightRule
Skills40matched / required; query skills get full credit, profile-only skills count at 0.6
Role / title20token overlap with job title, small capped bonus from the description
Domain15intent or profile domain matches job.domain
Experience10exact level 1.0, adjacent level 0.5, else 0
Location10exact/contains/remote 1.0; no stated preference is neutral at 0.6
Employment type5exact match

Bands: Strong ≥ 70, Good 50–69, Fair 30–49. Jobs below 30 are excluded from the ranked list; if nothing clears 30, the UI shows an explicit "no strong matches" state with the top 3 shown separately and labelled weak.

Explanations are assembled only from facts present in the breakdown — for example: "Matches 4 of 6 required skills (Python, FastAPI, PostgreSQL, Docker). Healthcare domain matches your interests. Senior level matches your 6 years of experience. Location differs: role is in Berlin, you prefer Remote." Mismatches are stated, not hidden.

Data model

users

id, email (unique), password_hash, role, company_name?, created_at

candidate_profiles

user_id (unique FK), name, headline, years_experience, skills[], education[], projects[], preferred_location, preferred_role_type, domain_interests[], skills_text (denormalized, lowercase, for filtering), updated_at

jobs

id, admin_id FK, title, description, required_skills[], skills_text, experience_level, location, employment_type, domain, company_name, status, timestamps

applications

id, job_id FK, candidate_id FK, status, cover_note, profile_snapshot, timestamps — UNIQUE(job_id, candidate_id), so duplicate prevention is enforced in the database, not only in service code

Technology stack and reasons

ChoiceReason

React Hook Form + ZodZod schemas validate the form and infer the TypeScript type; mirrors Pydantic on the backend

Deliberately excluded: Docker (a live-demo failure mode, and unnecessary once Postgres is out of the picture), Redis, Celery, a component library, a state-management library beyond TanStack Query + React context, an LLM SDK, axios.

Verification strategy

Automated (pytest, in-memory SQLite)

  • Pure scoring math, ranking order, band boundaries, weight sums
  • Intent extraction: specific query, vague query, empty query, unknown skills
  • Provider failure matrix: no key, timeout, 429, non-JSON, schema-invalid JSON, hallucinated skill
  • Application rules: duplicate, closed job, missing profile, every valid and invalid transition
  • Filters: each alone, all combined, none, no-results
  • Analytics against a known fixture, plus the empty-database case
  • Auth: role enforcement on every admin endpoint, ownership checks, bad token

Frontend: vitest on the API client's error mapping and the job-filter hook; tsc --noEmit; eslint.

Manual end-to-end

Both workflows exactly as specified in the brief, run start to finish on a freshly seeded database, at desktop and tablet widths.

Edge cases exercised by hand

Empty database, no open jobs, no matches, vague query, backend stopped mid-request (network failure), over-long description and project summary, a 40-skill list, invalid IDs typed into the URL.

Pre-submission gate — every command is run and its real output reported, and any failure is disclosed rather than hidden: ruff check · ruff format --check · pytest -q · npm run lint · npm run typecheck · npm test · npm run build · then a clean-environment startup following only the README.

Cross-platform

No Docker, no make, no shell scripts on the critical path — the seed is a Python script and everything else runs through npm/uvicorn. All paths go through pathlib. The README gives both PowerShell and bash venv activation lines. Dependencies are pure-Python or standard-library-backed, so there are no wheels to compile on Windows.
