Demo Script — Job Board with AI-Powered Candidate Matching

Read this during the Teams call. Everything below was run against the real seeded database before this document was written — the numbers are real, not illustrative.

Opening (30 seconds)

This is a job board with one differentiator: instead of filtering, a candidate describes the job they want in a sentence, and the system ranks every open role against that sentence with a score and a plain-English reason. I'll walk through the candidate side, then the admin side, then the matching engine itself.

    The system flags this as low-confidence rather than pretending it understood — that's a deliberate UI signal, not a silent failure.

Likely interview questions

Why isn't the ranking done entirely by the LLM?
The brief explicitly warns against putting essential ranking logic inside an untestable prompt. A weighted scorer is deterministic, unit-tested (25 tests pin the weights and ordering), and — critically for this evaluation — explainable in this conversation without hand-waving. The LLM is used only where fuzziness is the actual job: turning a sentence into structured fields.
What happens if OpenRouter is down or the key is missing?
The provider call has an 8-second timeout and every failure mode — no key, timeout, non-200, malformed JSON, schema-invalid JSON — falls back to a deterministic keyword extractor. This isn't a rarely-tested escape hatch: it's what's running in this demo right now, since no key is configured in this environment, and it's covered by the AI-provider failure-matrix tests in test_matching_provider.py.
How do you stop the explanation from inventing a skill the candidate doesn't have?
The explanation is assembled in Python from fields already on the score breakdown — matched skills, missing skills, domain match, location match. There's no LLM call in that path at all, so there's no mechanism by which it could state something the breakdown doesn't contain.
Why SQLite instead of Postgres?
The stated constraint was "works on Windows and Ubuntu without dependency issues." SQLite's driver ships with Python; Postgres would mean either Docker as a hard prerequisite or asking the evaluator to install and configure a database server before they can run the app. SQLAlchemy + Alembic keep Postgres a connection-string change away if this went to production.
Why scrypt instead of bcrypt for passwords?
bcrypt/passlib need a compiled native extension, which is the single most common Windows setup failure for Python projects. hashlib.scrypt is memory-hard and ships in the standard library — same security property, zero native dependency.
What's the biggest known limitation?
Skill and domain matching in the deterministic fallback is exact-keyword (word-boundary, case-insensitive) — "JS" won't match "JavaScript" unless both literal strings appear. With more time, the fallback's matching would move to embedding similarity while keeping the weighted-sum scorer as the actual ranking authority, since that's what stays testable and explainable.
How is admin-only access enforced?
Every admin route depends on a FastAPI dependency (CurrentAdmin) that checks the JWT's role server-side — not just a hidden button in the UI. Job and application mutations additionally check that the requesting admin owns the job in question; there are explicit tests for a second admin account being rejected with 403.
What would you build next given more time?
Embedding-based semantic matching for skills/domains, Postgres for real concurrent load, refresh tokens and password reset, and weights learned from real apply/hire outcomes instead of hand-set values.
